### What Worked vs. What Did NOT Work

#### What Worked:
1. **Compact Recurrent Structures (GRU):**
   * *Verified from source:* Unidirectional 2-layer GRUs ($d=128$ to $384$) consistently outperformed linear models, achieving $R^2 > 0.39$ compared to linear baselines at $0.32$ ([msrishav/wunder-rnn-gru-ensemble](https://huggingface.co/msrishav/wunder-rnn-gru-ensemble)).
2. **Causal 1D Convolution Front-ends:**
   * *Verified from source:* Preceding recurrent/state-space layers with a short causal 1D convolution smoothed microstructural noise and improved gradient stability ([KieranMalandain/mamba-lob-forecasting](https://github.com/KieranMalandain/mamba-lob-forecasting)).
3. **Loss Masking on Warm-Up:**
   * *Verified from source:* Allowing hidden states to accumulate through the warm-up steps while strictly evaluating loss only on scored steps was mandatory ([msrishav/wunder-rnn-gru-ensemble](https://huggingface.co/msrishav/wunder-rnn-gru-ensemble), [aicheye/wundernn](https://github.com/aicheye/wundernn)).
4. **Dimension & Seed Diversity Ensembling:**
   * *Verified from source:* Ensembling slightly varying hidden dimensions (e.g., $d=256$ and $d=384$) boosted cross-validated scores over any individual model by $\approx +0.003$ to $+0.005$ $R^2$ ([msrishav/wunder-rnn-gru-ensemble](https://huggingface.co/msrishav/wunder-rnn-gru-ensemble)).

#### What Did NOT Work:
1. **Linear Autoregressive Models (VAR / Ridge):**
   * *Verified from source:* Vector Autoregression ($\text{VAR}(p)$) and Ridge baselines saturated early around $R^2 \approx 0.32$, failing to capture high-order order book imbalances ([msrishav/wunder-rnn-gru-ensemble](https://huggingface.co/msrishav/wunder-rnn-gru-ensemble)).
2. **Standard Unmodified Transformers for Online Inference:**
   * *Inference:* While causal Transformers achieved competitive offline scores ($R^2 \approx 0.396$), caching full key-value attention histories over thousands of steps creates $O(T)$ or $O(T^2)$ memory and latency bloat, making them unsuitable for the tight single-vCPU online evaluation budget.
3. **Bidirectional Architectures:**
   * *Verified from source:* Any lookahead or non-causal operations violate the step-by-step streaming contract and cause catastrophic validation leakage or disqualification ([wundernn.io](https://wundernn.io/)).
4. **Naive First-Order Multi-Horizon Training:**
   * *Verified from source:* Training shared representations simultaneously on conflicting targets with plain AdamW suffered from gradient interference across horizons ([KieranMalandain/mamba-lob-forecasting](https://github.com/KieranMalandain/mamba-lob-forecasting)).

### Differentiable Loss Aligned with Global Weighted Pearson

* **Verified from source / mathematical derivation:** Standard Pearson correlation is invariant to arbitrary scale and shift. If trained solely on $-\rho_w$, networks can drift or produce unstable gradients near zero variance. A numerically stable, differentiable Weighted Pearson loss implementation in PyTorch is:

```python
import torch
import torch.nn as nn

class GlobalWeightedPearsonLoss(nn.Module):
    """
    Computes negative Weighted Pearson Correlation Loss matching wundernn.io metrics:
    w_i = |clip(y_i, -2.0, 2.0)|
    """
    def __init__(self, eps: float = 1e-8, clip_val: float = 2.0):
        super().__init__()
        self.eps = eps
        self.clip_val = clip_val

    def forward(self, y_pred: torch.Tensor, y_true: torch.Tensor) -> torch.Tensor:
        # 1. Clip predictions and targets in a differentiable manner
        y_p = torch.clamp(y_pred, -self.clip_val, self.clip_val).view(-1)
        y_t = torch.clamp(y_true, -self.clip_val, self.clip_val).view(-1)

        # 2. Derive non-negative weights according to metric definition
        weights = torch.abs(y_t)
        weight_sum = weights.sum() + self.eps
        w_norm = weights / weight_sum

        # 3. Weighted Means
        mean_p = torch.sum(w_norm * y_p)
        mean_t = torch.sum(w_norm * y_t)

        # 4. Centered Deviations
        dev_p = y_p - mean_p
        dev_t = y_t - mean_t

        # 5. Weighted Covariance and Variances
        cov = torch.sum(w_norm * dev_p * dev_t)
        var_p = torch.sum(w_norm * (dev_p ** 2))
        var_t = torch.sum(w_norm * (dev_t ** 2))

        # 6. Correlation with numerical stability guard
        corr = cov / (torch.sqrt(var_p * var_t) + self.eps)
        return -corr
```

* **Inference / Best Practice:**
  * **Hybrid Loss:** Combining Pearson loss with Huber loss ($\mathcal{L} = -\rho_w + \lambda \cdot \mathcal{L}_{\text{Huber}}$, e.g., $\lambda = 0.1$) prevents the model from generating unbounded scale drift while directly maximizing the competition metric.
  * **Network Output Activation:** Using a scaled `Tanh` (e.g., $2.0 \cdot \tanh(x)$) or `Hardtanh(-2, 2)` directly as the final output layer naturally enforces the $[-2, 2]$ clipping bounds during training and ONNX inference.

## 3. Practical Tips: Long-Sequence GRU Training & Single-Thread ONNX Inference

### A. Training on 20,000-Step Sequences: Truncated BPTT (TBPTT) with State Carry

1. **Chunking & State Propagation:**
   * Directly unrolling 20,000 steps causes GPU out-of-memory errors and gradient vanishing/exploding.
   * Divide the 20,000-step sequence into contiguous chunks of length $K$ (e.g., $K = 256$ or $512$).
   * For sequence $i$ and chunk $m$, pass the final recurrent hidden state of chunk $m-1$ to chunk $m$:
     ```python
     h_0 = h_n.detach()  # Disconnect graph history to bound memory to O(K)
     out, h_n = gru(chunk_x, h_0)
     ```
   * *Critical requirement:* Hidden states must be reset to zero ($h_0 = 0$) strictly at the start of each independent 20,000-step sequence.
2. **Warm-Up Masking:**
   * For the first 99 steps ($t \in [0, 98]$), execute the forward pass to build up the GRU hidden representation, but mask these steps out from loss computation and gradient backpropagation:
     ```python
     scored_mask = (step_indices >= 99) & (is_scored == 1)
     loss = criterion(y_pred[scored_mask], y_true[scored_mask])
     ```
3. **Gradient Management:**
   * Truncated backpropagation across carried hidden states requires strict gradient clipping (`torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)`).
   * Group independent sequences into batches (e.g., $B = 32$ parallel sequences) and process chunk $m$ across all $B$ sequences simultaneously.

### B. Single-Thread CPU ONNX Runtime Optimization

#### 1. Latency Budget Analysis
* **Given constraints:** 39,400,000 rows within 60 minutes (3,600 seconds) on 1 vCPU.
* **Required throughput:** $\approx 10,944 \text{ rows/sec}$.
* **Maximum latency per row:** $\le 91.37 \ \mu\text{s}$ (microseconds).
* *Inference:* Standard Python dictionary wrapping and repeated `session.run()` calls have an overhead of $10\text{–}25 \ \mu\text{s}$ per call. On 39.4M rows, Python overhead alone can consume 10–15 minutes of the 60-minute budget if not minimized.

#### 2. ONNX Runtime Session Configuration
Configure the ONNX Runtime session explicitly for single-threaded CPU execution:
```python
import onnxruntime as ort

opts = ort.SessionOptions()
opts.intra_op_num_threads = 1
opts.inter_op_num_threads = 1
opts.execution_mode = ort.ExecutionMode.ORT_SEQUENTIAL
opts.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
opts.enable_cpu_mem_arena = True

# Disable thread pool spinning if it causes OS scheduling thrashing on 1 vCPU:
opts.add_session_config_entry("session.intra_op.allow_spinning", "0")

session = ort.InferenceSession("model.onnx", opts, providers=["CPUExecutionProvider"])
```

#### 3. Low-Latency Execution Patterns
* **Pre-allocated NumPy Buffers:**
  Never reallocate NumPy arrays inside the step loop. Maintain pre-allocated static arrays for inputs and outputs and mutate them in-place:
  ```python
  input_buf = np.empty((1, 1, 112), dtype=np.float32)
  hidden_state = np.zeros((2, 1, 128), dtype=np.float32)

  # Inside step loop:
  input_buf[0, 0, :] = row_features
  preds, hidden_state = session.run(None, {"input": input_buf, "h_in": hidden_state})
  ```
* **I/O Binding (`io_binding`):**
  * *Verified from source:* Using `session.run_with_iobinding()` avoids per-step buffer verification and memory copy overhead ([ONNX Runtime I/O Binding Documentation](https://onnxruntime.ai/docs/api/python/api_summary.html#iobinding)).
* **Single-Step Cell Export vs. Sequence Graph:**
  Export a dedicated single-step GRU cell graph rather than passing sequence length $T=1$ through a variable-length sequence operator to eliminate shape-inference overhead:
  $$\text{Graph Input}: (x_t \in \mathbb{R}^{1 \times 112}, h_{t-1} \in \mathbb{R}^{2 \times 1 \times 128}) \longrightarrow \text{Graph Output}: (\hat{y}_t \in \mathbb{R}^2, h_t \in \mathbb{R}^{2 \times 1 \times 128})$$
* **Parameter Footprint & CPU Cache Locality:**
  * For a 2-layer GRU with input dim 112 and hidden dim 128:
    * Layer 1: $3 \times (112 \times 128 + 128 \times 128) \approx 92\text{k parameters}$
    * Layer 2: $3 \times (128 \times 128 + 128 \times 128) \approx 98\text{k parameters}$
    * Linear head: $128 \times 2 \approx 256\text{ parameters}$
    * Total: $\approx 190\text{k float32 values} \approx 760 \text{ KB}$.
  * *Inference:* 760 KB fits entirely within modern CPU L2/L3 cache, ensuring near-instantaneous memory access. Models with hidden dimensions $> 256$ or large ensembles risk cache evictions, causing memory-bus stalls that can breach the $91 \ \mu\text{s}$ limit.

## 4. Linear Recurrent Models in Streaming Competitions (LRU, Mamba, S5, minGRU)

| Architecture | Training Speed (20k steps) | Online 1-Step Complexity | ONNX CPU Export Feasibility | Observed Competition Status |
| :--- | :--- | :--- | :--- | :--- |
| **Vanilla GRU** | Slow (Sequential BPTT) | $O(1)$ | **Native / Flawless** | **Standard Baseline & Winner Choice** |
| **minGRU / minLSTM** | **Very Fast** (Parallel Scan) | $O(1)$ | **Native / Simple** | Strong theoretical match; under-explored in public repos |
| **Mamba / Mamba-2** | **Very Fast** (Parallel Scan) | $O(1)$ | **Difficult** (Requires unrolling) | Attempted in Wunder RNN Challenge & Jane Street |
| **LRU / S5** | **Very Fast** (Associative Scan) | $O(1)$ | **Poor** (Complex number ops) | Academic benchmarks; rare in production ONNX |

### Detailed Architecture Notes

1. **minGRU / minLSTM:**
   * *Reference:* Feng et al., *"Were RNNs All We Needed?"* (2024) ([arXiv:2410.01201](https://arxiv.org/abs/2410.01201)).
   * **Mechanism:** Removes the hidden state from gate definitions: $z_t = \sigma(W_z x_t)$, $\tilde{h}_t = W_h x_t$, and $h_t = (1 - z_t) \odot h_{t-1} + z_t \odot \tilde{h}_t$.
   * **Suitability:** Because gates depend solely on inputs, all projections are pre-computed in parallel across all 20,000 steps during training using a parallel prefix scan. In online inference mode, it degrades to an elementwise vector multiply-add.
   * **ONNX Compatibility:** Unlike Mamba, minGRU uses only standard linear layers and elementwise math, compiling into standard ONNX operators (`Add`, `Mul`, `Sigmoid`, `Tanh`) without custom kernels or runtime failures.
2. **Mamba / Mamba-2:**
   * *Reference:* Kieran Malandain's [mamba-lob-forecasting](https://github.com/KieranMalandain/mamba-lob-forecasting) (Wunderfund RNN challenge submission); [Jane Street Real-Time Market Data Forecasting 5th solution](https://www.kaggle.com/competitions/jane-street-real-time-market-data-forecasting/discussion).
   * **Practical Limitation for ONNX:** Standard PyTorch implementations depend on optimized CUDA scan kernels (`mamba_ssm`). Exporting to ONNX Runtime CPU requires rewriting the forward pass as an explicit recurrent loop, which often loses performance on CPU or introduces graph operator incompatibilities.
3. **LRU (Linear Recurrent Unit) & S5:**
   * *Reference:* Orvieto et al., *"Resurrecting Recurrent Neural Networks for Long Sequences"* (2023) ([arXiv:2303.06349](https://arxiv.org/abs/2303.06349)); Smith et al., *"Simplified State Space Layers for Sequence Modeling"* (2023) ([arXiv:2208.04933](https://arxiv.org/abs/2208.04933)).
   * **Practical Limitation:** LRU and S5 rely on diagonalized state transitions over the complex domain ($\mathbb{C}$). Complex arithmetic has uneven support across ONNX runtime execution providers, introducing overhead when emulated as paired real floats.

### Recommended Strategy
* **Primary / Safest Path:** Maintain the 2-layer GRU ($d \in [128, 160]$), using Truncated BPTT with hidden-state carryover, trained with `GlobalWeightedPearsonLoss` + Huber loss.
* **High-Upside Alternative:** Experiment with **minGRU** for order-of-magnitude faster parallel training over 20,000 steps while maintaining native, zero-risk ONNX CPU exportability.
